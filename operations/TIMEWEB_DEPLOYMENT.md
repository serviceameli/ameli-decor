# Публикация setdecor на Timeweb — кандидат

Исходная версия: `serviceameli/ameli-decor`, `main` / `64ad2f1273057ce5049cf563bcb1c97e4b82ee64`.

Существующий `.github/workflows/pages.yml` сохранён. Новый workflow не публиковался и не запускался. До проверки ручного размещения и HTTPS переменную репозитория `SETDECOR_TIMEWEB_READY` оставлять отсутствующей либо отличной от `true`.

## Необходимая серверная подготовка

- Сервер `217.149.19.37`, порт SSH `22`.
- Отдельная ограниченная учётная запись `setdecor-deploy`.
- Её ключ принимает только принудительную команду root-owned обработчика для этого сайта; обычный shell, sudo, Docker и доступ к Ameli OS не предоставляются.
- Серверная основа сайта: `/srv/ameli-sites/setdecor`; staging и releases находятся в той же файловой системе, что атомарно переключаемая текущая версия.
- Серверный обработчик проверяет манифест, размеры и SHA-256, отклоняет небезопасные пути и держит общий lock при переключении.
- Под lock он сравнивает поколение `(run_number, run_attempt)` и не позволяет старому запуску заменить более новый. Одна GitHub concurrency-группа сама по себе не гарантирует порядок всех запусков.
- Рабочий статический корень и отдельный маршрут Caddy должны быть согласованы и проверены. Этот workflow не меняет конфигурацию Caddy и не запускает deploy Ameli OS.

## Протокол передачи

SSH-команда: `deploy <40-символьный lower-case Git SHA> <run_number> <run_attempt>`.

В stdin передаётся первая строка UTF-8 JSON `{"schema":1,"commit":"<тот же SHA>","files":[{"path":"index.html","size":123,"sha256":"<SHA-256>"}]}` с LF. Следом идут необработанные байты файлов в порядке массива `files`, затем EOF. Передача не использует архивы.

Пути относительные, без начального `./`, без скрытых сегментов, `.`/`..`, обратной косой черты или дублей. Только обычные файлы. Лимиты обработчика: 3000 файлов, 200 МиБ общего содержимого, 1 МиБ заголовка.

`operations/stream_deploy.py` должен реализовать этот согласованный протокол. Путь `setdecor-release.json` зарезервирован сервером и не может приходить из исходной `dist`.

Контрольная сумма манифеста вычисляется по каноническому compact JSON: `json.dumps(manifest, sort_keys=True, separators=(',', ':')).encode('utf-8')`, без завершающего LF. Sender сохраняет локальный digest через `--manifest-sha256-output` перед первым байтом передачи; workflow сравнивает его с ответом SSH-обработчика и публичным marker. Это отдельный хеш; он не равен хешу текстового списка `sha256sum`.

## GitHub

1. Проверенный публичный host key сохранён в `operations/known_hosts`; он перенесён из прежнего закреплённого подключения, а не получен с сети во время публикации.
2. Секрет `TIMEWEB_DEPLOY_KEY` — отдельный ограниченный ключ публикации. Личный административный ключ и backup-ключ не использовать.
3. Окружение workflow: `setdecor-production`. Его политика должна разрешать только production-ветку `main`.
4. Репозиторная переменная `SETDECOR_TIMEWEB_READY=true` включается только после принятого cutover и проверки публичного HTTPS.
5. Workflow проверяет текущий `main` перед сборкой и непосредственно перед передачей. Устаревший запуск ничего не публикует.
6. SSH-обработчик возвращает JSON со статусом `deployed` либо `already_current`, ожидаемым commit, поколением и `manifest_sha256`. Workflow проверяет этот ответ, затем строго проверяет HTTPS и `/setdecor-release.json`: `commit`, `run_number`, `run_attempt`, тот же `manifest_sha256`. Проверка TLS не отключается.

Код завершения обработчика: 0 — успех, 2 — неверный либо устаревший запрос, 75 — обработчик занят, 1 — внутренняя ошибка. Неуспешный результат останавливает публикацию. Внешняя сетевая ошибка после переключения сама по себе не запускает откат: сначала требуется установить, какой релиз реально активен. Серверный rollback допускается только для той же ожидаемой неудачной версии, чтобы не затронуть более новый запуск.

Ошибка публичной проверки помечает workflow как неуспешный, но оставляет активную версию на сервере. После диагностики возможен ограниченный rollback только для точного ожидаемого tuple `(commit, run_number, run_attempt)`. Другую, уже более новую версию он менять не должен.

Изменение переменной READY само не запускает workflow. После её включения отдельно выполнить `workflow_dispatch` для `main` и подтвердить первый успешный полный проход. Весь job ограничен десятью минутами; серверный обработчик также должен иметь ограничение ожидания/времени и отменять неполную загрузку до переключения.

Сборка идёт на GitHub с Node 22; на VPS исходники не компилируются. Пакет сейчас не имеет зависимостей и lock-файла, поэтому `npm ci` не используется. Если зависимости появятся, отдельным изменением добавить lock-файл и проверенную установку.

## Проверка перед включением

- Серверный обработчик и sender согласованы и проверены; ограничения действуют для реального ключа.
- Ручной кандидат отдаёт ожидаемые index/content/assets; SHA-256 совпадают.
- Проверены HTTPS, изображения и кадрирование, выбор комплекта, копирование заявки, PDF.
- Известна предыдущая рабочая версия и проверен порядок отката.
- Предыдущие assets сохраняются достаточно долго: старый HTML или JS в браузере не должен терять изображения после переключения.
- Pages workflow сохраняется до завершения cutover; его отключение — отдельный явный шаг.
